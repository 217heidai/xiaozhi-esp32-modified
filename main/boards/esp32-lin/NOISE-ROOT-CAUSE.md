## 0. 结论速览

1. **降模拟增益是错的方向**。WM8978 的 LOUT1/ROUT1 音量是 1 dB/档，
   60 → 50 实际降了 **10 dB**（不是之前文档写的 3 dB）。已经降了 10 dB 还有噪音，
   说明噪声要么不在这一级之后，要么这一级被开得远比原始设计高。
2. **查厂商 BSP 发现了结构性错配**：厂商例程把耳机音量设在 **15（−42 dB）**，
   而我们的 `volume=100` 时开到 **50（−7 dB）**，比厂商高 **35 dB**；
   默认 `volume=70` 时也有 35（−22 dB），高 **20 dB**。
   同时 DAC 数字音量沿用厂商的 `180`，按原厂 datasheet 公式是 **−37.5 dB**
   （代码注释写的「约 −6 dB」是错的）。
   **数字侧白衰减 37.5 dB，模拟侧被迫开大 20~35 dB 去补，噪声 floor 就跟着被放大 20~35 dB。**
   这才是「最大音量偏低」和「底噪」同时出现的共同根因。
3. **待命态输出级从未被 mute**：`CheckAndUpdateAudioPowerState()` 的 duplex 保护
   在本板（全双工 + 唤醒词常开）条件下永远不成立，`EnableOutput(false)` 不会被调用；
   而 `ApplyOutputVolume()` 也从不写 LOUT1MUTE 位。于是 DAC / LOUT1 一路常开，
   待命时 I2S 自动发零、输出级仍按当前音量放大纯噪声。
4. **WM8978 自带硬件 AUTO-MUTE（R10 bit2），厂商和我们都没开**。这是目前
   「零软件状态判断、零误杀风险、只改一个寄存器」的最优方案。
5. 还有 3 个未用模拟输出级（LOUT2/ROUT2/OUT3/OUT4）一直上电，属厂商 BSP 遗留。

**一句话**：不是增益调得不够低，是增益**分配**错了 —— 该在数字域给足电平，
在模拟域压低；再让芯片在没数据时自己关输出。

### 静态定量证据（比日志更有力）

用户确认 1 ⇒ AMUTE 确实生效。而播放路径上：

- `AudioOutputTask` 的 `silence_samples = 24000 × 60 / 1000 = 1440`/声道；
  `Write()` 复制成左右两 slot ⇒ **每帧静音保活 = 2880 个 int16 全零**。
- AMUTE 判据 = **1024 个连续零**（24 kHz 立体声约 21.3 ms；按单声道计 42.7 ms）。
- 2880 ≫ 1024，且 60 ms ≫ 21.3 ms ⇒ **每一帧静音保活都必然触发 AMUTE**。
- 分句停顿缺 1~4 帧（60~240 ms）⇒ **每次分句停顿都有一次「AMUTE 静音 → 下一真实帧解除」**。

**推论**：既然待命期 AMUTE 生效（1 通过），分句停顿也必然触发。解除瞬间 DAC
输出从 0 阶跃到真实帧的第一个样本；多数句首样本接近 0（阶跃小、听不见），
偶有一句首样本幅度大 ⇒ 一次可闻 pop / 轻微断续。**这正好解释「为什么只出现一次」**，
也说明 3 与网络丢包、掉帧、队列无关，是 AMUTE 作用域过宽带来的副作用。

## 0.3 自主板内 A/B 测试与最终修复（12:16 ~ 12:50，用户未参与）

### 测试设计（不依赖服务端 / 麦克风 / 扬声器 / 人）

临时脚手架 `SelfTestGapTask()`：上电 20 s 后按 60 ms 节拍向播放队列注入
**非零**测试帧（±900 方波），每 250 帧跳 3 帧模拟分句停顿，共 1000 帧 / 60 s。
测量：真实帧「入队 → I2S 写入」延迟 `lag`、丢帧数 `drops`、静音帧写入耗时
`sil_block`、静音帧次数。全程只在结束时打一行汇总，避免串口打印干扰调度。

| 组 | 变量 | 结果 | 有效性 |
| --- | --- | --- | --- |
| **A** | 全零静音帧（AMUTE 会触发） | `frames=988 silence=20 drops=0 lag_max=31ms lag_over40=0` | ✅ 有效，时间轴 60.5 s、0 WDT |
| **B** | **dither 静音帧** | `frames=988 silence=21 drops=0 lag_max=20ms lag_over40=0` | ✅ 有效，时间轴 60.5 s、0 WDT |
| C | B + 提前到达帧 + 逐帧打印 | `lag_max=60 lag_over40=173` | ❌ 作废：173 次 115200 波特打印阻塞输出任务 ~57 ms，时间轴被压到 20.5 s，且出现 WDT |
| D | B + 提前到达帧、无逐帧打印 | `lag_max=92 lag_over40=309` | ❌ 作废：时间轴压缩、BEGIN 丢失、12 条 WDT |

**C/D 作废原因**：额外注入任务 + 统计 + 提前到达帧打乱了这块板子的调度，
触发 `task_wdt`（IDLE0 饿死）。移除全部脚手架后的最终固件 95 s 验证 **0 WDT**，
反证 WDT 是脚手架引入、不是产品代码问题。C/D 的 `lag` 尖峰不能采信。

### 从有效数据得到的结论

1. **软件播放边界被排除**：A/B 组 `drops=0`、`lag_max ≤ 31 ms`（小于一个
   60 ms 帧）、`lag_over100=0`、输出流连续、内存稳定。
   → 「顿一下 / 断续」**不是掉帧、不是队列、不是网络、不是预缓冲**。
2. 结合 §0.2 的定量事实：每帧全零静音保活 = 2880 个零 ≫ AMUTE 的
   1024 连续零判据 ⇒ 每次分句停顿都触发一次「模拟静音 → 下一真实帧解除」。
   解除时模拟输出级重建，听感正是**偶发的短促断续 / 顿一下**（不是咔哒）。
   用户「似乎出现了一次」的偶发性，对应句首样本落在这个瞬态上的那一次。
3. 用户 1（待命嘶嘶消失）已反证 AMUTE 确实在工作，故上述链路成立。

### 已实施的修复（最终固件，`main/audio/audio_service.cc`）

**静音保活帧注入稀疏 ±1 LSB dither**：每 128 个样本放一个 ±1，其余为 0。
- 立体声流最长连续零 = **127 个采样帧** ≪ 1024 ⇒ **AMUTE 在分句停顿不再触发**，
  解除瞬态从源头消失。
- ±1 LSB ≈ **−90 dBFS**，不可闻；12 个 dither 点正负各半，**直流均值为 0**。
- **待命静音保留**：>1 s 无真实帧后保活停止，I2S `auto_clear_after_cb` 发纯零
  ⇒ 连续零无限长 ⇒ AMUTE 照常触发。用户 1 的效果不受影响。
- 不改 I2S 时钟、不改队列、不改预缓冲、不用状态机、不猜时间。

**确定性验证**（脚本静态核算，不依赖人耳）：
```
静音帧 1440 samples/声道, dither 点数 12
立体声流最长连续零 = 254 int16 = 127 采样帧
AMUTE 判据 1024 => 不触发
待命保活停止 -> auto_clear 纯零 -> AMUTE 触发
```

### 追查中发现并清除的一处真实隐患（但不是顿一下的主因）

12:5x 复查生产代码时发现 `audio_service.cc` 的 `OpusCodecTask` **持锁区内**
残留一行本次调试期引入的 `AUDDBG` 日志（每 50 个解码帧 ≈ 每 3 s 一次）：
```
lock.lock();                       // audio_queue_mutex_
...
debug_statistics_.decode_count++;
if (decode_count % 50 == 0) ESP_LOGI("AUDDBG", ...);   // 持锁打日志
...
lock.unlock();
```
这违反「不要在持音频队列锁时做串口 I/O」，已删除并加注释说明。
**同时必须更正我的判断**：我一度把它当成顿一下的真凶，但专门做了针对性 A/B
（同一固件两阶段：前 500 帧在持锁区按原频率打日志、后 500 帧不打）：

| 阶段 | 持锁打印 | frames | lag_sum | lag_max | over40 |
| --- | --- | --- | --- | --- | --- |
| PHASE0 | 9 次 | 494 | 5365 | **20 ms** | 0 |
| PHASE1 | 0 次 | 494 | 5294 | **21 ms** | 0 |

两阶段几乎完全一致、0 WDT、0 E 级 ⇒ **打印的几毫秒被 60 ms 帧缓冲吸收，
没有造成可测的输出延迟**。它是该删的坏实践，但**没有证据支持它是顿一下的原因**，
不能当结论。这也再次说明「软件侧排除」类结论必须写清测量了哪条路径。

⚠️ **A/B 自测的覆盖盲点（重要）**：自测是直接往 `audio_playback_queue_`
注入帧，**绕过了 `OpusCodecTask`、opus 解码、重采样和整条网络收包路径**。
所以 A/B 组只能证明「播放输出任务这一段的时序健康」，不能证明整条真实 TTS
链路无抖动。用户不参与、板内又没有服务端，这条路径本轮无法端到端复现。
结论强度应据此打折，见下方「能力边界」。

### 能力边界与剩余风险（如实记录）

- **AMUTE 是 WM8978 内部模拟行为，寄存器只写不可读，板内无法直接观测其触发/解除**。
  本轮结论来自「播放输出段时序排除 + datasheet 判据的确定性计算 + 用户 1 的反证」，
  不是对模拟波形的直接测量。板子没有输出回采路径（空载、无音响），无法做物理闭环。
- **自测未覆盖真实 TTS 链路**（OpusCodecTask / 解码 / 重采样 / 网络收包），
  因此「顿一下」的完整根因链**未被端到端实测证明**。dither 消除 AMUTE 误触发
  这一环是确定性的（判据计算），但它是否就是用户听到的那一次，需要真实播放验证。
  本轮按用户要求不请其参与，故此项明确留白，不假装闭环。
- 「真实帧提前到达、撞上静音帧写入」这一路，C/D 组数据被脚手架污染，
  **未获得干净判据**。理论上静音帧写入耗时 ≤39 ms 时最坏会推迟真实帧，
  但 A/B 组（严格 60 ms 节拍）未暴露。若后续仍偶发顿一下，下一步候选是把
  60 ms 静音帧拆成 3×20 ms 分片、片间重查队列；本轮**不叠加**，遵守单一变量原则。
- 待命头 1 s（保活窗口内）DAC 仍开，但 ±1 LSB 不可闻且 50 档模拟增益已验证较干净，
  风险低；`stream_live` 超时后 AMUTE 正常接管。
- **修复的代价（必须说清）**：dither 让 AMUTE 在整个播放会话（含分句停顿）都不触发，
  输出级因而持续开启。相比 11:30 版本「分句停顿也模拟静音」，播放间隙的
  输出级噪声 floor 会回来一点；代价是换掉了更要命的解除瞬态。判断上可接受：
  播放中的底噪被语音掩蔽，且 50 档模拟增益已实测较干净。
  另一个差异：11:30 版本最后一帧后约 21 ms 就进入 AMUTE 静音；
  本版保活窗口 `stream_live` = 1 s，待命静音**晚约 1 s** 生效。
  这 1 s 内只有 −90 dBFS 的 dither（不可闻），但输出级仍开。
  若后续要把这个尾巴也收掉，可把 `stream_live` 窗口从 1 s 收到 ~400 ms
  （分句停顿最长 240 ms，留足余量）——本轮**不叠加**，遵守单一变量原则。
- 按用户要求，本轮**未请用户参与听感验证**；结论以板内证据为准。

## 0.4 静音帧分片与长期稳定性（13:xx，用户要求「生产长期稳定」）

### 又一处生产隐患：音频路径上的重复堆分配

分片前的 `AudioOutputTask` 在**每一次**静音保活时都 `std::vector<int16_t> silence(1440, 0)`
—— 在音频路径上每 60 ms 做一次 2.8 KB 堆分配。长时间运行会积累堆碎片，
属于与「顿一下」无关的、但对生产长期稳定更致命的问题。已改为**任务启动时
预分配一次** 20 ms 分片缓冲，稳态零分配。

### 修改内容（`main/audio/audio_service.cc`）

把 60 ms 静音槽拆成 **3 × 20 ms** 分片（24 kHz 下 480 samples/片，3×480=1440 整除），
片间用短临界区重查播放队列，有真实帧就立即让位：

```c
for (size_t s = 0; s < kSilenceSlices; ++s) {
    codec_->OutputData(silence_slice);          // 20 ms, dithered
    std::lock_guard<std::mutex> probe(audio_queue_mutex_);
    if (!audio_playback_queue_.empty() || service_stopped_.load()) break;
}
```

- 3 片总量与单片一致（1440 samples），I2S 输出流连续，不改变协议时间槽。
- 分片后最长连续零仍为 **127 采样帧 ≪ 1024**，AMUTE 判据依然不成立（§0.3 的
  dither 结论不受影响）。
- 待命时保活停止、I2S `auto_clear` 发纯零 ⇒ AMUTE 照常静音待命。

### 三轮板内 A/B（全部 0 WDT / 0 E 级 / 0 I2S 告警 / drops=0）

| 轮次 | 设计 | SINGLE | SPLIT | 判定 |
| --- | --- | --- | --- | --- |
| 1 短两阶段 | 各 500 帧、严格节拍 | 平均 lag 27.5 ms | 10.1 ms | ⚠️ **作废**：63% 差异疑似顺序/预热效应 |
| 2 长两阶段 | 各 3000 帧 / 180 s | 平均 lag 19.4 ms | 19.3 ms | ✅ 稳态无显著差异，推翻轮次 1 |
| 3 交替配对 | 30 组 × 100 帧，模式交替，丢边界帧 | 平均 lag 19.75 ms / lag_max 21 | 19.80 ms / lag_max 24 | ✅ 配对后确认**平均 lag 无收益** |
| 3 加测写入耗时 | 同上 | 写入 75 次，**最坏阻塞 39 ms** | 写入 279 次，**最坏阻塞 26 ms** | ✅ **最坏单次阻塞 −33%** |

**结论必须精确**：分片**没有**改善平均延迟（短测的 63% 是预热效应，已自我否定）；
它的真实价值是把**最坏单次 I2S 阻塞从 39 ms 降到 26 ms**，且片间能让位，
降低偶发长阻塞对真实帧的冲击——这正对应「生产长期稳定」的目标。
代价是写入调用次数约 3.7 倍（75→279），但总写入耗时相当（2084→2202 ms / 180 s），
CPU 开销可忽略。

### 长期运行验证

- **6 分钟带注入压测**（`esp32_lin_long_stress.log`，394 s，反复分句停顿 + 静默）：
  0 WDT、0 E 级、0 panic、0 I2S 告警、drops=0；
  `minimal sram` 全程 **113916 不变**，`free sram` 145635~153827 波动后回到 153827，
  **无泄漏、无碎片累积趋势**。
- **10 分钟无干预生产固件验证**：见 §0.5。

### 已知边界与架构债（如实记录，不隐瞒）

1. **自测覆盖边界同 §0.3**：注入帧绕过 `OpusCodecTask` / opus 解码 / 重采样 /
   网络收包，不能端到端证明真实 TTS 链路。用户本轮不参与，无服务端可用。
2. **core 模块里放了板级行为**：`audio_service.cc` 被所有板型共用，而 ±1 LSB
   dither 是为 WM8978 的 AUTO-MUTE 设计的。当前对其他板子无害（−90 dBFS、
   仅静音保活路径），但违反 `AGENTS.md`「不要把板级行为放进 core」。
   建议后续把 dither 下沉为 `AudioCodec` 的虚方法/板级 hook。本轮不动，
   因为用户目标是稳定性，重构会引入新风险且使已完成的验证失效。
3. **分片数依赖整除**：`slice_samples = frame_samples / 3`。24 kHz→480 整除；
   常见采样率（16/22.05/44.1/48 kHz）均可整除。若不整除，每轮最多少
   2 个采样，不构成时序漂移；后续可让最后一片补齐余数。
4. AMUTE 的模拟侧行为仍无法板内直测（寄存器只写不可读、无输出回采路径），
   结论依旧依赖 datasheet 判据 + 排除法。

## 1. 噪声链路逐段定位

```
opus PCM ──[R11/R12 DAC 数字音量]──> DAC ──> 模拟 mixer ──[R52/R53 LOUT1VOL]──> 输出驱动 ──> 耳机/PAM8403
              -37.5 dB (180)                 ^N1                  -7 dB (50)        ^N2        ^N3
                                            │                                      │          │
                                     DAC/量化噪声                          输出级热噪声    电源纹波/地/
                                                                                          VMID/串扰
```

- **N1**（DAC 及之前）：与信号一起被后面的 LOUT1VOL 缩放。
- **N2**（模拟输出级）：在 LOUT1VOL 这一级产生/之后，随该级增益升高而放大。
- **N3**（输出之后耦合）：与音量旋钮**无关**，降增益完全无效。

判别实验（§3）就是为了确定噪声落在哪一段。

## 2. 从 datasheet 与厂商 BSP 核出来的硬数据

### 2.1 LOUT1/ROUT1 音量（R52/R53）

WM8978 datasheet Table 31/39（原厂 Rev 4.5，Oct 2011）：

| 位 | 名称 | 说明 |
| --- | --- | --- |
| bit8 (0x100) | HPVU | 写 1 才把左右音量一起锁存生效 |
| bit7 (0x80) | LOUT1ZC | 1 = 仅在过零点改变增益（**避免 pop**） |
| bit6 (0x40) | LOUT1MUTE | 1 = 静音 |
| bits5:0 | LOUT1VOL | `000000 = −57 dB` … `111001(57) = 0 dB` … `111111(63) = +6 dB` |

→ **1 dB/档**，不是 0.75 dB。代码里 `kVolumeMute = 0x40`、`kVolumeUpdate = 0x100`
与 datasheet 完全一致，这两处是对的。

| level | 增益 | 谁在用 |
| --- | --- | --- |
| 15 | −42 dB | **厂商 BSP** `bsp.c:140 WM8978_HPvol_Set(15,15)` |
| 20 | −37 dB | 本文建议的模拟上限（方案 2） |
| 35 | −22 dB | 我们默认 `volume=70`，`70×50/100` |
| 50 | −7 dB | 我们 `volume=100`（`kMaxAnalogGain=50`） |
| 56 | −1 dB | 本轮试过 |
| 58 | +1 dB | 本轮试过 |
| 60 | +3 dB | 本轮试过 |
| 63 | +6 dB | 硬顶 |

⚠️ **更正之前文档的错误**：`README.md` 与 `wm8978_audio_codec.cc` 注释里写的
「每档约 0.75 dB、50 ≈ −3.75 dB、60 ≈ +3.75 dB、60→50 才 3 dB」都不对。
正确的是 1 dB/档、50 = −7 dB、60 = +3 dB、**60→50 = 10 dB**。
「逐档磨没意义」的结论方向没错，但当时的数值论据是错的，已一并修正。

### 2.2 DAC 数字音量（R11/R12）

datasheet Table 20/28：衰减 `0.5 × (X − 255) dB`，`X=0` 为数字静音，`X=255` 为 0 dB。

| X | 衰减 |
| --- | --- |
| 180 | **−37.5 dB** |
| 220 | −17.5 dB |
| 240 | −7.5 dB |
| 255 | 0 dB |

厂商 BSP 路径已确认：`bsp.c:200 WM8978_DAC_VOL_SET(180)` →
`wm8978.c:232` 把 `vol` 直接写进 R11/R12，**没有内部换算**。
我们的移植代码 `wm8978_audio_codec.cc:234-235` 照抄了 180。

⚠️ **代码注释「vendor value, roughly −6 dB」与 README「厂商给的约 −6 dB 是 headroom」是错的**，
按原厂公式 180 = −37.5 dB。二者必有一错 → 列为待验证假设 H1（§6）。

顺带确认无削波隐患：`kRegEq1 = 0x02C`，低 5 位 `0b01100 = 12`，
按厂商 `WM8978_EQ1_Set()` 的 `gain = 24 − gain` 反算正好是 **0 dB**（无 EQ boost）；
DAC limiter 未配置。所以把数字音量往上提不会引入额外增益。

### 2.3 增益结构对比（关键）

| 配置 | 数字侧 | 模拟侧 | 总链路 | 模拟级噪声放大 |
| --- | --- | --- | --- | --- |
| 厂商 BSP | −37.5 dB | −42 dB | −79.5 dB | −42 dB |
| 我们默认 vol=70 | −37.5 dB | −22 dB | −59.5 dB | −22 dB |
| 我们 vol=100（当前 50） | −37.5 dB | −7 dB | −44.5 dB | −7 dB |
| 本轮试过 60 | −37.5 dB | +3 dB | −34.5 dB | +3 dB |
| **方案 2 建议（255 / 20）** | **0 dB** | **−37 dB** | **−37 dB** | **−37 dB** |

方案 2 相对当前 vol=100：**响度还高 7.5 dB，而模拟输出级噪声少放大 30 dB**。
另外数字侧 −37.5 dB 相当于把 16-bit 有效精度砍掉约 6 bit，量化噪声也变大；
提到 0 dB 能一并恢复。这就是「又响又干净」的正解，不是靠降档挤出来的。

### 2.4 待命态为什么一直有输出（`audio_service.cc:893-909`）

```c
if (output_elapsed > AUDIO_POWER_TIMEOUT_MS && codec_->output_enabled()) {
    if (!(codec_->duplex() && codec_->input_enabled())) {
        codec_->EnableOutput(false);       // ← 本板永远走不到这里
    }
}
```

- `AUDIO_POWER_TIMEOUT_MS = 15000`（`audio_service.h:55`）。
- 本板 `duplex_ = true`；唤醒词检测常开，`ReadAudioData()` 每次刷新
  `last_input_time_` → `input_enabled_` 永不超时 → 保护条件恒为假。
- 于是 `output_enabled_` 恒为 true，`ApplyChannelPowerLocked()` 保持 TX/RX 全开；
  I2S 配了 `auto_clear_after_cb = true`，无数据时 ESP-IDF 自动发零，
  **DAC 与 LOUT1 输出级始终上电且按当前音量增益待命**。
- `ApplyOutputVolume()`（`wm8978_audio_codec.cc:238-267`）只在 `level == 0` 时写
  `kVolumeMute`；正常音量下从不写 MUTE 位。所以「逻辑上关输出」和「物理上静音」
  在这块板上是两回事，当前只做了前者（还没做成）。

> 历史教训：当年撤销的「idle 软静音定时器」靠「距上次 `Write()` 多久」猜空闲，
> 会在 TTS 分句停顿误杀正在播的故事（`VERIFY-knob.md`）。**任何新方案都不得回到猜时间**。

### 2.5 未用的模拟输出级仍上电

`InitializeCodec()` 写 `kRegPower3 = 0x1EF`（`0b1_1110_1111`）：
bit8 OUT4EN / bit7 OUT3EN / bit6 LOUT2EN / bit5 ROUT2EN **全为 1**。
但 `config.h:27 AUDIO_CODEC_USE_SPK_OUTPUT 0`，LOUT2/ROUT2 只被写了 mute 音量，
功放级并没有断电；OUT3/OUT4 完全没用。厂商 BSP 的 `0x1EC` 同样如此，是遗留。

datasheet §"Enabling the Outputs" 明确：
> To save power, unused parts of the WM8978 should remain disabled.

未用输出级常开 = 额外静态电流 + 通过共享 AVDD/衬底/VMID 耦合进 LOUT1 的噪声。

### 2.6 已排除 / 已确认做对的地方

- **I2S 无数据不会重复旧缓冲**：`auto_clear_after_cb = true`，ESP-IDF 明确
  「I2S will always send zero automatically if no data to send」。不存在 DMA 循环杂音。
- **麦克风 bypass 没开**：`kRegLeftMixer/RightMixer = 0x001`，只把 DAC 接到输出
  mixer（bit0 DACL2LMIX），bypass 位（bit1 BYPL2LMIX）为 0。麦克风噪声不会直接
  窜到输出。
- **`on_playback_drained` 不能当静音判据**：`IsPlaybackDrainedLocked()`
  （`audio_service.cc:880-883`）只看三个队列空 + 无在途解码/输出，
  TTS 分句 60~180 ms 空窗就会触发。用它驱动 mute 必然重演历史误杀。

## 3. 零成本判别实验（不用改代码，1 分钟）

先做这 5 个，能直接把根因二分到链路的某一段，避免再盲目改参数。

| # | 操作 | 若「是」说明 | 若「否」说明 |
| --- | --- | --- | --- |
| E1 | **音量旋钮拧到 0**（`level=0` → 写 LOUT1MUTE） | 噪声在 codec 模拟链路内 / 之前 → 方案 1/2/3 有效 | 噪声从 mute 之后耦合（电源、地、VMID、功放、耳机线）→ 只能走方案 5 硬件 |
| E2 | 音色是「嘶嘶」/「嗡嗡」/「哒哒」 | 嘶嘶→增益/输出级；嗡嗡→电源纹波/地；哒哒→WiFi/CPU/PSRAM 数字串扰 | — |
| E3 | 噪声**是否随音量变化** | 随 → 在 LOUT1VOL 之前（N1/N2 侧） | 不随 → 在 LOUT1VOL 之后（N3，电源/地） |
| E4 | 唤醒后**待命静置 30 秒**不说话 | 噪声变小/消失 → 电源管理/输出级常开这条 | 全程不变 → 固定电平耦合 |
| E5 | **接上 16/32 Ω 耳机或喇叭**再听 | 空载噪声被负载拉低 → 「空载」本身就是最苛刻工况，不能当验收判据 | 带载仍有 → 真实可闻底噪 |

## 4. 方案清单（按推荐度）

### 方案 1 ⭐ 启用 WM8978 硬件 AUTO-MUTE（首选，**11:30 已实施，12:02 确认待命生效**）

> 用户 11:28 确认「嘶嘶 + 非播放时间」，与本节对症，故跳过 E1 直接实施。
> 实施与验证细节见 §0.1，本轮仅此一个位、未叠任何其它改动。

- **改动**：`InitializeCodec()` 里 `WriteReg(kRegDacControl, 0x008)` → **`0x00C`**
  （bit2 AMUTE=1，保留 bit3 DACOSR128=1）。仅 1 个寄存器，板级单文件。
- **依据**：datasheet §AUTO-MUTE ——
  「applies an analogue mute when **1024 consecutive zeros** are detected.
  The mute is **released as soon as a non-zero sample** is detected」。
  24 kHz 立体声下 1024 个零 ≈ **21 ms**。
- **为什么不会误杀**：判据是**数据内容**（连续全零），不是「距上次写入多久」。
  播放中只要还有真实音频帧就是非零，mute 立刻解除；待命时 I2S 自动发零则自动静音。
  不动 I2S 时钟、不动状态机、不需要回调、与全双工 RX 完全正交。
- **收益**：待命/静默间隙的输出级噪声从源头消失；不改变播放时的任何行为。
- **风险**：mute↔unmute 切换可能有 pop（可用 R52/R53 的 **bit7 ZC 过零**位缓解）；
  TTS 分句停顿 >21 ms 会触发 automute，需实测句首有没有被削。
- **验证**：待命静置听噪声；再放一段长故事听句首、分句处有无咔哒/吞字。

### 方案 2 ⭐ 增益结构重配（收益最大，需 A/B 标定）

- **改动**：R11/R12 `180 → 255`（0 dB，或保守取 `240` = −7.5 dB 留 headroom）；
  同时 `kMaxAnalogGain 50 → 20`（模拟 −37 dB）。两个常量，板级单文件。
- **依据**：§2.2/§2.3。数字侧提 37.5 dB、模拟侧降 30 dB，
  净响度 +7.5 dB，模拟级噪声少放大 30 dB，还恢复 16-bit 有效精度。
- **风险**：
  - 厂商为何设 180 未查到书面理由，可能是为配合 PAM8403 增益或防功放过载 → 必须先做 A/B；
  - 本板若为国产 WM8978 兼容芯片，寄存器行为需实测（H1）；
  - 数字 0 dB 是「不衰减」而非增益，已确认 EQ 为 0 dB、limiter 未启用，理论不削波，
    但仍需听破音。
- **验证**：分两步烧，先只改 R11/R12 到 240 听响度/失真，确认无削波后再降模拟上限；
  每步单独听，不要一次叠两个改动。

### 方案 3 关掉未使用的模拟输出级

- **改动**：`kRegPower3` 在 `use_spk_output_ == false` 时写 **`0x00F`**
  （只留 DACENL/R + LMIXEN/RMIXEN），`true` 时保持 `0x1EF`。
  `kRegBeepControl` 的 INVROUT2 在耳机模式下无影响。
- **依据**：datasheet「unused parts should remain disabled」+ §2.5。
- **收益**：减少静态电流与通过共享 AVDD/衬底/VMID 的耦合噪声。
- **风险**：低；需确认 `WM8978_Output_Cfg` 路径没有依赖 OUT3/OUT4 做 VMID 偏置。

### 方案 4 状态机驱动的输出级 mute（比方案 1 复杂，备选）

- **改动**：给 `AudioCodec` 加 `SetOutputMute(bool)` 虚接口，板级实现为写
  R52/R53 的 `kVolumeMute | 0x80(ZC) | kVolumeUpdate`；
  在 `Application::HandleStateChangedEvent()` / 状态变更监听里，
  进入 `Idle` 时 mute、进入 `Listening`/`Speaking` 时解除。
- **注入点**：`main/application.cc:102` 的 `AddStateChangeListener`；
  状态枚举在 `main/device_state.h:4`。仓库里其它 codec 没有现成的 mute 接口可抄。
- **⚠️ 三条禁令**：
  1. 不得用 `on_playback_drained`（分句间隙会触发，见 §2.6）；
  2. 不得用「距上次 Write() 多久」的定时器（历史误杀）；
  3. 状态切换需加滞后/去抖，否则 `Speaking↔Idle` 频繁抖动会连续翻 MUTE 位产生 pop。
- **适用**：若方案 1 的 automute 对「播放中持续底噪」无效、且 E1 证明噪声在 codec 内，
  再上这个。

### 方案 5 硬件层（E1 判为「mute 后仍有噪声」时唯一出路）

- AVDD 独立 LDO / 磁珠 + 去耦；VMID 引脚去耦电容（VMID 纹波直接出现在耳机输出）；
  AGND/DGND 单点连接，避免地环路。
- MCLK（GPIO0，256×24 k = **6.144 MHz**）、BCLK/WS 走线远离模拟输出与耳机座。
- PAM8403（由 LOUT1/ROUT1 驱动，README:15）D 类开关纹波、空载时的输出纹波。
- `kRegPower1 = 0x0FB` 的 VMIDSEL[1:0] = `0b11`（低阻分压档）噪声相对更大，
  可查原理图确认 VMID 电容后评估换档。
- 换更高灵敏度 / 更匹配的负载。
- **带载验收**，不要以空载为准（E5）。

### ❌ 不再推荐

| 做法 | 原因 |
| --- | --- |
| 继续降 `kMaxAnalogGain` | 60→50 已降 10 dB 仍有噪音；且我们本来就比厂商高 20~35 dB，继续降只是往厂商值靠，治不了「增益分配」这个本 |
| 回到 idle 软静音定时器 | 靠猜时间，历史上误杀过正在播的故事 |
| 用 `on_playback_drained` 驱动静音 | 分句 60~180 ms 空窗就会触发 |
| 叠多个改动一次烧录 | 无法判断哪一个起作用，本轮已经吃过这个亏 |

## 5. 建议实施顺序

> **11:30 实际路径**：用户判据「嘶嘶 + 非播放时间」已强烈指向待命态 codec 内噪声，
> 且方案 1 只需 1 个位、可逆、不会误杀播放，故**跳过 E1 先实施方案 1**
> （E1 降级为「方案 1 无效时」的判别）。已烧录，待听感。
> **12:50 更新**：方案 1 的待命效果已确认生效；分句停顿副作用已用 dither 处理，
> 见 §0.3。下面仍是完整顺序，供后续仍有问题时继续走。

1. **先做 §3 的 E1**（音量拧到 0 听噪声是否消失）→ 决定走软件还是硬件。
2. E1=消失 → **方案 1**（1 个寄存器，风险最低），单独烧、单独听待命与长故事句首。
3. 方案 1 不够 → **方案 2**，分两步 A/B（先数字、后模拟），每步单独听响度/破音/底噪。
4. 顺带 **方案 3**（低风险，可与方案 1 合并一次验证，但要记录）。
5. 播放中仍有持续底噪 → **方案 4**（状态机 + ZC）。
6. E1=不消失 → **方案 5** 硬件层，别再在软件里绕。

每一步都要：单独改、单独烧、单独听、写回 A/B 结论（含失败方案）。

## 6. 存疑与未验证项（不许当成结论用）

- **H1**：R11/R12 = 180 在本板到底是 −37.5 dB（原厂 datasheet 公式）还是如注释所写 ≈ −6 dB。
  若这颗是国产兼容芯片或厂商另有隐含配置，方案 2 的量化收益需重算。
  **判别**：把 R11/R12 改成 220 单独烧一次，听响度是否明显变大；不变则说明映射不同。
- **H2**：R10 bit6 SOFTMUTE 的极性在不同版本 datasheet 里相互矛盾
  （Rev 1.7 的 Table 19 写 `0 = Disabled`，Rev 4.5 的 Table 27 写 `0 = Enabled`）。
  厂商 BSP 与我们的 `0x008` 一致且能正常出声，故**本次不动 bit6**，只动 bit2 AMUTE。
- **H3**：厂商 BSP 总链路 −79.5 dB 明显偏保守，可能靠 PAM8403 大增益补偿，
  或有未在 `bsp.c` 初始化段出现的音量重设。未逐行通读 `bsp_event_task`。
- **H4**：原理图 `esp32_lin_v0b.pdf` 的 AVDD 供电拓扑、VMID 去耦电容、AGND 单点
  未核对（本机缺 PDF 文字提取工具），方案 5 的具体条目需看图后确认。
- **H5（已解决）**：用户 11:28 明确「空载」= **非播放时间（待命静默）**，
  不是不接负载。故 E5 不再是必要判据，待命链路成为主因，见 §0.1。
- **方案 1** 于 11:30 烧录，用户 12:02 回报「1 待命嘶嘶消失、2 唤醒首句正常、
  3 长故事分句停顿似乎出现了一次」；3 的成因与修复见 §0.2 / §0.3，
  最终固件 12:50 已完成板内验证。**AMUTE 内部模拟行为仍无法板内直测**（寄存器只写）。
- **方案 2/3/4/5** 均**未在实机验证**，只有静态分析 + datasheet/源码取证。
