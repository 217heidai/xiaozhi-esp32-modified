# 音频播放连续性排查手册（板级 A/B 自测法）

> 适用场景：移植/自研板子上出现「播放中顿一下」「断了不能恢复」「长故事中途静音」
> 「起播慢半拍」这类**音频连续性**问题，且手上只有板子、没有第二块对照板、
> 没有示波器、没有人帮你听。
>
> 本文是从 `esp32-lin` 板（ESP32-WROVER + WM8978）移植过程中踩坑总结的可复用流程，
> 案例细节见 `main/boards/esp32-lin/README.md`「播放中偶发『顿一下』：根因与修复」。
> 目的是让下一个维护者**不重复走错方向**。

---

## 0. 一句话原则

**先把「现象」变成「可测量的物理判据」，再去找根因；在判据建立起来之前，任何参数调整都是赌博。**

本项目在这个原则上栽过两次：一次是把协议允许的序列号跳号当成网络丢包（方向错，两周白干），
一次是把应用层「取帧节奏」当成 I2S 断流（判据错，A/B 结论反着读）。

---

## 1. 第一步：把症状切成可判定的类别

症状描述越模糊，越容易一开始就选错方向。先逼自己归类：

| 症状 | 首要怀疑层 | 第一步动作 |
| --- | --- | --- |
| 断了**不能恢复**，必须重启/重新唤醒 | 状态机 / 看门狗 / 通道被关 | 抓 `listening/speaking` 状态迁移日志，看有没有卡在中间态 |
| 周期性**短促顿一下**（60~200 ms），之后照常播 | 输出流断流（供给不足或时钟停） | 建 I2S 实际写速率监控 |
| **全程**没声音或只有一边 | codec 配置 / slot 映射 / 功放使能 | 查 I2S slot 模式与 codec 输出路由 |
| 起播**慢半拍**（唤醒后 1~2 s 才出声） | 预缓冲 / 通道建立 / 重采样初始化 | 打时间戳看各阶段耗时 |
| 播放**发空、发糊、有回音** | 双麦相位 / AEC 状态 / 采样率不匹配 | 对照单路输入试听 |
| 音量异常（调不动 / 过小 / 破音） | codec 增益寄存器 / 功放输入范围 | 直接读回寄存器值确认写入生效 |

> 关键区分：「**不能恢复**」几乎都是状态机或电源管理问题；「**能自己恢复的短促断流**」
> 才是供给链问题。两类混在一起查，必翻车。

---

## 2. 铁律一：先读数据源语义，再读设备端处理链

**顺序不能反。** 设备端代码是自己写的，看着最眼熟，最想先改；但错往往在「上游给的东西
被我理解错了」。

检查清单：

1. **协议/API 文档原文读一遍**，特别是「容错」「异常处理」小节里那句被当成废话的话。
   本项目里 `docs/mqtt-udp_zh.md` 4.3「允许轻微的序列号跳跃」、4.4「序列号异常仍处理数据包」，
   两句直接决定了「跳号」是**正常语义**还是**故障**。
2. **验证上游字段的真实规律**，不要靠猜。本项目实测 18 条接收基线，确认
   `timestamp == sequence × 60 ms` 严格成立 → `sequence` 是**时间槽编号**，
   于是「跳号」= 上游跳过了空槽（TTS 分句停顿），不是丢包。
3. **在设备端搜「上游给了这个字段，谁在消费它」**。本项目的 `timestamp` 从收包一路传到
   解码任务，唯一引用点在 `#if CONFIG_USE_SERVER_AEC` 分支里，而该项未开启
   → **时间轴被整条丢弃**，播放退化成「收一帧播一帧」。这就是根因。
4. **反向验证假设**：如果假设成立，日志里应该出现什么？本项目预测「缺口间隔 ≈ 缺帧数 × 60 ms」，
   实测 660~840 ms 对上了 `d_seq` 的 1~4 帧缺口 → 假设成立。

> 一句经验：**凡是「上游字段只有某个可选功能在用」的地方，关掉那个功能就等于把语义扔了。**

## 3. 铁律二：判据必须是物理量，不能是应用层计数

应用层看到的是「我取了几帧」，物理层发生的是「I2S 有没有停」。两者不是一回事：

- 队列空了但 I2S 还在吐上一帧剩下的 DMA 数据 → 应用层看起来「没断」，实际已经在断。
- 应用层注入静音帧 → 取帧计数很好看，但如果注入点在下游已经断流之后，物理上照样断。

**可用的物理判据（按可获得性排序）**：

1. 记录每次 `i2s_channel_write()` 的**实际写入字节数 × 频率**，折算 B/s，与满速
   （`sample_rate × channels × bytes_per_sample`，本项目 24000×2×2 = 97920 B/s）比对；
   低于满速的窗口即真实断流。
2. 如果有条件：示波器/逻辑分析仪看 BCLK/LRCK 是否连续、功放输入端是否有直流跳变。
3. 没有仪器时，退一步用「断流窗口的时间戳序列」作为判据：连续 N 个采样周期的速率下探
   才算一次，单点抖动不算。

**计数纪律**：一次「断流」的定义要写死在脚本里（阈值、最小持续、去抖窗口），
否则同一份日志两个人能数出两个数，A/B 结论就没有意义了。

## 4. 铁律三：板内自测 —— 不依赖服务端 / 麦克风 / 扬声器 / 人

这是本项目最有价值的一条：当「能调动的硬件只有这块板子」时，**把刺激源也搬进板子里**。

### 4.1 脚手架设计要点

- **自造匀速流**：起一个 `SelfTestTask`，按真实帧率（本项目 60 ms）自己生成静音 PCM 帧，
  直接注入播放队列，`timestamp = slot × 60 ms`。
- **注入可复现的「坏事件」**：每 N 帧跳过 k 个时间槽，模拟上游分句停顿；间隔、次数固定写死。
- **等系统稳定再开始**：上电 20 s 后启动，避开初始化期的通道建立、重采样预热。
- **A/B 两阶段，刺激完全相同**：同一份固件，只切换待测开关；A 段 60 s、B 段 60 s，
  切换点单独标记（切换瞬间的队列重置会产生一次假断流，判读时要排除）。
- **不用扬声器也能判**：判据是 I2S 写速率，不是耳朵。这样自测可以无人值守跑，
  也不受环境噪声影响。

### 4.2 反面：不要用真人对话做 A/B

- 服务端 TTS 每次内容不同、分句位置不同、网络状况不同 → 不可比。
- 真人听感只能作为**最终主观验收**，不能作为定位手段。
- 本项目正确顺序：先用板内自测把「断流次数 3 → 0」证死，再让人听一遍确认「不再顿」。

## 5. 铁律四：统计上不显著，就是无效

调参最容易骗自己的地方：**短测改善 ≠ 有效**。

判读纪律：

- 除了相对比例，**必须看绝对次数**。本项目 WiFi 缓冲 6/8/6 → 16/32/16，
  归一化丢包率 8.06 → 5.66 次/分看着降了，但**绝对次数同为 9 次**，泊松 95% 区间大幅重叠 → 无效。
- 记录**波动幅度**。同一配置重跑，短测波动能到 6.8 倍时，单次 A/B 差值毫无意义。
- 样本量不够就别下结论，宁可写「未观测到显著差异」，也不要写「已优化」。

---

## 6. 铁律五：调参前先算「稳态存货」

这是「加大队列」类尝试失败的根本原因：

> 匀速流（60 ms 到达 / 60 ms 消费）下，队列**稳态深度 ≈ 0**。
> 上限从 2 加到 6 只是允许它临时攒货，攒不起来货就没得用。

所以凡是「缓存/队列/缓冲」类参数，动之前先回答两个问题：

1. 到达速率和消费速率的**长期均值**差多少？（差 0 → 队列永远见底）
2. 我的问题需要多少 ms 的存货才能扛过去？（需求 > 可得 → 调参无用，必须改机制）

本项目结论：只有「队列空时立刻保活输出流」这种**机制改动**才能解决，
单纯加大上限从 3 → 2 次断流，不根治。

## 7. 逐层排查清单（自下而上，不要跳层）

**L0 供电与时钟**
- [ ] 排线/焊点：I2S、I2C、功放供电是否有虚焊（本项目烧过两块板才确认）
- [ ] codec 主时钟：MCLK 是否由 MCU 提供、频率与采样率是否成整数比
- [ ] 全双工时 RX 的 BCLK/LRCK 由谁提供（很多 codec 是 RX slave，关掉 TX 就把录音时钟一起掀了）

**L1 驱动层**
- [ ] 阻塞调用是否有超时（`portMAX_DELAY` 在通道异常时就是死锁）
- [ ] 写/读失败后能否自愈（重建通道、重试寄存器写入）
- [ ] 电源管理：`EnableOutput(false)` / `EnableInput(false)` 是否会误关共用时钟
- [ ] slot 模式与 codec 声道数是否匹配（mono + 单 slot → 只有一边响）

**L2 服务/任务层**
- [ ] 播放任务的等待方式（无限 `wait()` → 队列空即永久休眠，无法感知断流）
- [ ] 有没有看门狗以「真实帧」为准（注入的静音帧不能算进度，否则掩盖真实饥饿）
- [ ] 起播预缓冲帧数与真实帧率的关系
- [ ] 采样率转换（16k → 24k）在哪一层做，缓冲深度多少

**L3 协议层**
- [ ] 上游字段语义读完（见第 2 节）
- [ ] 时间轴字段是否真的有人消费
- [ ] 跳号/重排/去重策略是否与协议文档一致（本项目 `duplicate/old` 恒 0，说明重排逻辑多余）

**L4 网络层**
- [ ] lwIP 接收 mbox 深度 vs WiFi RX buffer 是两回事，别混
- [ ] 静态/动态 RX buffer、BA 窗口：默认值可能是照抄别的芯片（本项目通用 defaults 里
      写着「copied from ESP32C3 to reduce memory」——对 4 MB PSRAM 的板子就是错配）
- [ ] 收包任务优先级是否被别的任务饿死

**L5 芯片性能**
- [ ] CPU / flash / PSRAM 频率是否已拉到目标上限
- [ ] 注意部分配置项在 `sdkconfig.defaults` 里不生效（被 confgen 判为 not visible 而静默丢弃），
      需要走板级 `config.json` 的 `sdkconfig_append` 或构建目录下的 defaults 覆写机制

> 顺序纪律：**先证明下层是好的，再怀疑上层。** 反了就会像本项目早期那样，
> 在 L4 网络层折腾两周，真正的病灶在 L3 一句话里。

## 8. 反面清单（本项目实证无效，别重复）

| 尝试 | 实测结果 |
| --- | --- |
| 播放队列上限 2 → 4 → 6 | 断流 3 → 2 → 2，部分缓解不根治（稳态存货 ≈ 0） |
| CPU 160 → 240 MHz、flash/PSRAM 40 → 80 MHz | 顿挫无变化（WDT 归零了，现象还在） |
| lwIP `UDP_RECVMBOX_SIZE` 6 → 32 + 收包提权 | 归一化 4.03 → 1.44 次/分，短测波动 6.8 倍，不显著 |
| WiFi RX buffer 6/8/6 → 16/32/16 | 8.06 → 5.66 次/分，绝对次数同为 9，泊松区间重叠，**无效** |
| 协议层按 sequence 重排 | `duplicate/old` 恒 0，晚到旧包根本不存在 |
| 依赖 opus 原生 PLC | 反汇编确证 vendor 库不读 `frame_recover` 参数 |
| **事后补静音**（下一帧到了才补上一段缺口） | 断流 4 → 2，机制错：断流已经发生，补不回来 |

> 特别提醒：`SO_RCVBUF` 在 lwIP 里是**上限判断**，不是扩容手段。想靠它「加大接收窗口」
> 是空想——这一点被用户一句话点破过。

## 9. 修完必须做的三件事

1. **拆脚手架**：自测任务、临时打印、A/B 开关全部删干净；`sdkconfig` 里为诊断加的东西
   要么删、要么写进板级配置并注明原因。判据是编译 0 warning、串口日志干净。
2. **留数据**：把 A/B 三组数字写进文档，包括**失败的方案**。失败数据比成功数据更值钱
   ——它能挡住下一个人重走这条路。
3. **写清「未验证项」**：本项目明确标注「官方 S3 板串口日志未抓过」「真人长对话听感未录」，
   并指出「根因与修复不依赖这两条」。**诚实标注边界，比假装闭环更专业。**

## 10. 一页速查

```
症状
 ├ 不能恢复 ────────────→ 状态机 / 电源管理 / 看门狗（L1-L2）
 ├ 能自愈的短促断流 ────→ 输出流供给（L2-L3），先算稳态存货
 ├ 全程无声/单边 ───────→ slot 与 codec 路由（L1）
 ├ 发空/发糊 ───────────→ 输入相位、AEC、采样率（L1-L2）
 └ 音量不对 ────────────→ 寄存器回读确认写入（L1）

动手前必答三问
 1. 上游这个字段的语义，文档原文怎么写的？
 2. 我的判据是物理量还是应用层计数？
 3. 这个改动的效果，能被统计证明吗（绝对次数 + 区间）？
```
